# eBlocul — сервер

Backend приложения жилого комплекса: NestJS, Prisma, PostgreSQL.

Правила, по которым пишется код, лежат в `CLAUDE.md` и `.claude/rules/`. Здесь только то, что нужно, чтобы поднять проект.

## Что нужно на машине

- Node.js 24 — в CI и в образе стоит 24.21.
- PostgreSQL 18 на `localhost:5432` — та же версия, что в CI.
- Docker — для Mailpit, локального почтового ящика.

## Первый запуск

1. Установить зависимости. Заодно создаётся клиент Prisma и включается проверка перед коммитом.

    ```bash
    npm ci
    ```

2. Создать две пустые базы: рабочую и для e2e-тестов.

    ```sql
    CREATE DATABASE "eblocul-server";
    CREATE DATABASE eblocul_e2e;
    ```

3. Создать файл окружения и заполнить в нём `AUTH_JWT_SECRET`: 32 символа или больше, например вывод `openssl rand -hex 32`. Если у PostgreSQL другие пользователь и пароль, поправить `DATABASE_URL`.

    ```bash
    cp .env.example .env.local
    ```

4. Создать `.env.e2e` для тестов с двумя строками:

    ```
    NODE_ENV=e2e
    DATABASE_URL=postgresql://postgres:postgres@localhost:5432/eblocul_e2e
    ```

5. Применить миграции к рабочей базе.

    ```bash
    npm run prisma:deploy
    ```

6. Поднять Mailpit. Письма приложения приходят в него: http://localhost:8025.

    ```bash
    docker compose -f docker-compose.dev.yml up -d
    ```

7. Запустить API.

    ```bash
    npm run start:dev
    ```

Проверить, что всё поднялось:

- http://localhost:3000/api/v1/health отвечает `{"status":"ok"}`;
- http://localhost:3000/swagger открывает описание API. OpenAPI в JSON — http://localhost:3000/swagger-json.

## Процессы

Образ один, процессов три. У каждого своя точка входа.

| Что                 | В разработке               | Собранное                   | Зачем                                              |
| ------------------- | -------------------------- | --------------------------- | -------------------------------------------------- |
| API                 | `npm run start:dev`        | `npm run start:prod`        | HTTP-запросы                                       |
| Исполнители заданий | `npm run start:worker:dev` | `npm run start:worker:prod` | фоновые задания из очереди; без него они не идут   |
| Наполнение базы     | `npm run seed`             | `npm run seed:built`        | выдуманные данные для `lab`; запускается и выходит |

## Окружения

Окружение задаёт `NODE_ENV`. От него зависит, какие файлы читаются.

| `NODE_ENV`   | Файлы                          | Где                             |
| ------------ | ------------------------------ | ------------------------------- |
| `lab`        | `.env.local`, затем `.env.lab` | локально и на lab-сервере (dev) |
| `production` | `.env.production`              | production                      |
| `e2e`        | `.env.e2e`                     | тесты; в CI — переменные задачи |

В git попадает только `.env.example`. Приложение не стартует, если переменной нет или её значение неверно: в сообщении об ошибке названа переменная.

## Наполнение базы

`npm run seed` запускает сиды — выдуманные данные, на которых работают фронт и приёмка. Сиды пишутся так, чтобы повторный запуск не создавал дублей. В `production` она ничего не пишет и завершается с ошибкой.

Сейчас список сидов пуст: данные добавляют модули по мере появления. Как написать сид — `.claude/rules/seeds.md`.

## Проверки

| Команда                | Что проверяет                               |
| ---------------------- | ------------------------------------------- |
| `npm run lint`         | правила кода и границы модулей              |
| `npm run typecheck`    | типы                                        |
| `npm run format:check` | форматирование                              |
| `npm test`             | unit-тесты, база не нужна                   |
| `npm run test:e2e`     | e2e-тесты на базе `eblocul_e2e`             |
| `npm run build`        | сборка                                      |
| `npm run knip`         | неиспользуемые файлы, экспорты, зависимости |

Перед коммитом формат, lint и типы изменённых файлов проверяются сами. В CI на каждый PR идут все проверки и сборка образа Docker.

e2e-тесты сами применяют миграции к `eblocul_e2e` и очищают её перед каждым тестом. Рабочую базу они не трогают.

## База и миграции

- Схема лежит в `prisma/schema/`, по файлу на модуль.
- Новая миграция после правки схемы: `npm run prisma:migrate`.
- Применить существующие миграции: `npm run prisma:deploy`.
- Посмотреть данные: `npm run prisma:studio`.

Правила для схемы и миграций — `.claude/rules/schema.md` и `.claude/rules/migrations.md`.

## Ветки

`main` — выпущенное, `dev` — следующий выпуск. Работа идёт в ветке `feature/<модуль>-<что>` или `fix/<модуль>-<что>` от `dev`, PR — обратно в `dev`. Подробнее — `CLAUDE.md`.
