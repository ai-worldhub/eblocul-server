# API

## Маршруты

- Ресурсы — во множественном числе и kebab-case: `/houses`, `/access-codes`.
- Параметр пути назван по сущности: `:houseId`, а не `:id`.
- Данные текущего пользователя — под `/me`. Его id берётся только из сессии, через `@CurrentSession()`: в пути, query и теле его нет.
- Переход состояния, который не сводится к правке поля, — `POST` на глагол: `/requests/:requestId/reopen`. Правка полей — `PATCH`.

## Сессия и доступ

- Каждый эндпоинт несёт ровно одну пометку доступа:
    - `@Public()` из `shared/http` — открытый: сессию не читает;
    - `@SessionOnly()` из `shared/http` — нужна только сессия: `/me/session`, `/me/access`;
    - `@Access(ДЕЙСТВИЕ)` из `authz` — данные дома: нужны сессия и основание.
- Сессию требует общий guard модуля `identity`, основание и право на действие — общий guard модуля `authz`; он идёт вторым и отклоняет запрос до контроллера.
- Кто пришёл, контроллер узнаёт только через `@CurrentSession()`. Cookie и заголовок `Authorization` читают только guard и контроллеры входа и выхода в `identity`.
- Браузер получает идентификатор сессии только в cookie `eblocul_session`. Ставит и стирает её только `identity`; в теле ответа идентификатора нет.
- Сессия принимается только тем путём, каким выдана. Закрытый эндпоинт и выход отвечают 401 на запрос, в котором есть и cookie, и `Authorization`.
  Открытый эндпоинт сессию не читает: вход с обоими заголовками проходит по email и паролю, `Authorization` в нём ничего не значит.
- Изменяющий запрос с cookie — любой, кроме `GET`, `HEAD` и `OPTIONS`, — принимается только с `Origin` из `WEB_PANEL_ORIGINS`.
  Открытый эндпоинт, который вызывает браузер, помечен `@RequireTrustedOrigin()`: у входа cookie ещё нет.
- У каждого способа входа свои эндпоинты под `/auth/<приложение>/`: `/auth/admin-panel/login`. Приложения — `admin-panel`, `guard-panel`, `resident-app`.
- Приложение жильца получает идентификатор сессии в теле ответа на вход — и только в нём — и шлёт его как `Authorization: Bearer <token>`.
- Вход жильца — четыре шага под `/auth/resident-app/`: `codes`, `login`, затем `registration` или `consent`.
  До верного кода ответ не зависит от того, зарегистрирован ли номер.
- Числа группы `auth` несёт декоратор `@AuthRateLimit()` модуля `identity`: литерал в контроллере не повторяется.
- Своя сессия — `/me/session`: `GET` читает, `DELETE` завершает. Свои роли — `GET /me/access`: список оснований; у аккаунта без ролей он пуст.

### Доступ к данным дома

- Основание — запись о роли человека: назначение на узел или привязка к объекту. Запрос действует ровно одним основанием:
  клиент называет его id в заголовке `X-Access-Grant`. Права двух оснований не складываются.
- Действие объявляет модуль-владелец в `application/<модуль>.actions.ts` и вносит в `src/app/access-actions.ts`.
  У действия есть вид — чтение или изменение — и охваты для каждой роли. Изменяющее действие председателю не даётся.
- Цель в пути называется в пометке: `{ node: 'nodeId' }` или `{ unit: 'unitId' }`.
- Область видимости контроллер берёт через `@CurrentAccess()` и передаёт в сервис. Каждый метод запроса к данным дома
  принимает `AccessScope` и ставит его условием запроса: `scopeCondition` для сырого SQL, `scopeWhere` для Prisma.
- Изменение первой строкой транзакции вызывает `AccessService.confirm(tx, access)`: он перепроверяет основание и цель,
  держит их до конца транзакции и возвращает область видимости, вычисленную заново.
  Запросы этой транзакции ставят её, а не `access.scope`: область от guard к этому моменту могла устареть.
  Цель, которой нет в пути, передаётся третьим аргументом.
- Собрать `AccessScope` вне `authz`, сравнить роль или узел в модуле — ошибка.

```ts
export const TICKET_CHANGE_STATUS = defineAction({
    name: 'tickets.change_status',
    kind: 'change',
    grants: {
        administrator: ['perimeter'],
        chief_administrator: ['quarter_node', 'unadministered_nodes', 'taken_zones'],
    },
});

@Post(':nodeId/tickets/:ticketId/close')
@Access(TICKET_CHANGE_STATUS, { node: 'nodeId' })
close(@CurrentAccess() access: AccessContext, @Param() params: CloseTicketParams): Promise<TicketResponse> {
    return this._tickets.close(access, params.ticketId);
}

return this._transactions.run(async (tx) => {
    const scope = await this._access.confirm(tx, access);
    const ticket = await this._tickets.lockById(tx, scope, ticketId);
    …
});
```

Ответы guard доступа одинаковы у всех эндпоинтов с `@Access`; пометка сама описывает их в Swagger:

| Статус и `code`              | Когда                                                               |
| ---------------------------- | ------------------------------------------------------------------- |
| 400 `AUTHZ_GRANT_REQUIRED`   | заголовка `X-Access-Grant` нет                                      |
| 403 `AUTHZ_GRANT_NOT_ACTIVE` | основание чужое, неизвестное, прекращённое или не этого приложения  |
| 404 `AUTHZ_TARGET_NOT_FOUND` | цель вне видимости или не существует; ответ одинаков, `details` нет |
| 403 `AUTHZ_ACTION_FORBIDDEN` | цель видна, но роль действие здесь не даёт                          |

## Ограничение частоты

- Лимит по адресу клиента ставит декоратор `@RateLimit({ group, burst, refillSeconds })` из `shared/http`:
  `burst` — сколько запросов проходит подряд, `refillSeconds` — за сколько секунд возвращается один запрос.
- Открытый эндпоинт без пометки живёт по общему лимиту: всплеск 60, один запрос в секунду.
- Вход, отправка кода и его проверка несут пометку группы `auth`: всплеск 30, один запрос в 2 секунды.
- Эндпоинты одной группы тратят одно ведро на адрес и несут одинаковые числа. Группа на двух эндпоинтах — числа в одной константе.
- `@NoRateLimit()` снимает лимит. Он только для эндпоинтов, которые опрашивает мониторинг: `health`, `metrics`.
  Другого открытого эндпоинта без лимита нет.
- На закрытых эндпоинтах общего лимита нет. Лимит по аккаунту или объекту считает сервис — см. `modules.md`.
- Эндпоинт, на котором действует лимит, описывает 429 через `ErrorResponse`: это эндпоинт с `@RateLimit` и открытый эндпоинт без пометки.
  Эндпоинт с `@NoRateLimit()` 429 не описывает: вернуть его он не может.

```ts
@Post('admin-panel/login')
@Public()
@RateLimit({ group: 'auth', burst: 30, refillSeconds: 2 })
@ApiTooManyRequestsResponse({ type: ErrorResponse })
```

## Коды ответа

| Операция                      | Код                   | Тело               |
| ----------------------------- | --------------------- | ------------------ |
| `GET`                         | 200                   | ресурс или список  |
| `POST`, который создал запись | 201                   | созданная запись   |
| `POST`-действие               | 200, `@HttpCode(200)` | новое состояние    |
| `PATCH`                       | 200                   | обновлённая запись |
| `DELETE`                      | 204, `@HttpCode(204)` | нет                |

Кроме 204, ответ всегда с телом: клиент получает новое состояние без второго запроса.

## DTO

Всё, что сервер принимает и отдаёт, описано DTO. Ответ, собранный из объекта без DTO, — ошибка.

- DTO одной сущности лежат в одном `namespace`: `presentation/dto/<сущность>.dto.ts`.
- Внутри: сущности без суффикса (`House.Card`), тела запросов `<Что>Request`, ответы `<Что>Response`.
- У каждого класса `@ApiSchema({ name: '<Namespace>-<Класс>' })`, иначе одинаковые имена сталкиваются в Swagger.
- На полях запроса — декораторы `class-validator`; на всех полях — `@ApiProperty` или `@ApiPropertyOptional`.
- Вложенный объект в запросе — `@ValidateNested()` и `@Type(() => …)`, иначе его поля не проверяются.
- Метод контроллера объявляет DTO и в `@ApiOkResponse({ type })`, и в типе возврата.
- У каждого метода `@ApiOperation({ summary })`, а у контроллера `@ApiTags`.
- Каждый статус ошибки, который может вернуть метод, описан через `ErrorResponse`. Метод, который принимает путь, query или тело, описывает 400.

```ts
export namespace House {
    @ApiSchema({ name: 'House-Card' })
    export class Card {
        @ApiProperty({ example: '0192f0c1-7b3a-7c11-9a41-2f6d3c8e5b10' })
        id: string;

        @ApiProperty({ type: String, nullable: true, example: null })
        activatedAt: Date | null;
    }
}

@Get(':houseId')
@ApiOperation({ summary: 'Read one house' })
@ApiOkResponse({ type: House.Card })
@ApiBadRequestResponse({ type: ErrorResponse })
@ApiNotFoundResponse({ type: ErrorResponse })
read(@Param('houseId', ParseUUIDPipe) houseId: string): Promise<House.Card> {
    return this._houses.read(houseId);
}
```

## Имена полей

Поля запросов и ответов — в camelCase и называются так же, как поля модели Prisma.
Если имя или значение в ответе отличается от модели, это делает маппер
`presentation/mappers/<модель>.mapper.ts`, а не `@Expose`.

## Списки

- Запрос: `limit` от 1 до 100 (по умолчанию 20) и `cursor` из прошлого ответа. DTO запроса наследует `ListQuery`; фильтры — явные query-параметры.
- Ответ: `items` и `nextCursor`; `null` значит, что страниц больше нет. Общего числа записей нет.
- Сортировка фиксирована: `createdAt desc, id desc`. Параметра сортировки нет.
- Запрос берёт `limit + 1` записей, `toCursorPage` отрезает лишнюю. Нужен индекс по полям фильтра и сортировки.
- Курсор разбирается через `decodeCursor`; сломанный курсор — 400 `INVALID_CURSOR`.

## Проверяется автоматически

- `tsc`: возвращаемый объект совпадает с DTO, если тип возврата указан.
- `ValidationPipe`: лишние поля запроса отбрасываются, границы `limit` проверяются.
- `test/e2e/openapi/openapi.e2e-spec.ts` по той же схеме, что уходит клиенту:
    - у каждой операции есть `summary`, тег и уникальный `operationId`;
    - успешный ответ ровно один и ссылается на DTO, у 204 тела нет;
    - любая описанная ошибка ссылается на `ErrorResponse`;
    - 400 описан у каждой операции со входом;
    - параметры пути названы и имеют схему;
    - ни одна схема, кроме enum, не пуста.

- Запуск приложения: пометка с числами, которые нельзя посчитать, и разные числа у одной группы не дают стартовать.
- Запуск приложения, `test/e2e/authz/access-marks.e2e-spec.ts`: не стартует эндпоинт без пометки доступа и с двумя пометками,
  действие чтения не на `GET` и изменения на `GET`, действие не из списка, два действия с одним именем, цель без параметра в маршруте.
- `test/unit/authz/access-actions-registry.spec.ts`: каждое действие из `*.actions.ts` внесено в `src/app/access-actions.ts`.
- `tsc`: `AccessScope` нельзя собрать вне `authz` — у типа закрытый ключ.
- `test/e2e/throttle/rate-limit-marks.e2e-spec.ts`: общий лимит у открытого эндпоинта без пометки, числа из декоратора,
  одно ведро на группу, `@NoRateLimit()`.

## Не проверяется

- Стиль маршрутов и коды ответа; `@HttpCode` у действий и удаления.
- 429 в описании эндпоинта с лимитом; вход без пометки `auth`; `@NoRateLimit()` на эндпоинте, который мониторинг не опрашивает.
- `@Public()` на эндпоинте, который должен быть закрыт; открытый эндпоинт для браузера без `@RequireTrustedOrigin()`.
- `@SessionOnly()` на эндпоинте с данными дома; охват действия шире, чем положено роли.
- Метод запроса к данным дома без `AccessScope`; изменение без `AccessService.confirm`;
  запрос в транзакции изменения с областью от guard, а не от `confirm`.
- Что у метода указан тип возврата: без него `tsc` не сравнивает ответ с DTO.
- Что описаны ошибки, кроме 400: тест видит только описанное и не знает, что метод бросает 404 или 409.
- Имя в `@ApiSchema`: при совпадении имён остаётся одна схема, и тест этого не замечает.
- `limit + 1` и индекс у списка.
