# Модули и их границы

## Два вида модулей

- **Ядро** — `src/core/<модуль>/`: `identity`, `structure`, `membership`, `authz`, `tenancy`,
  `journal`, `jobs`, `recovery`, `files`, `notify`, `throttle`.
- **Прикладные** — `src/modules/<модуль>/`: `account`, `onboarding`, `billing`, `announcements`,
  `chats`, `tickets`, `guard`, `video`, `polls`, `neighbors`, `gates`, `governance`, `assistant`, `backoffice`.

Зависимости направлены вниз: `app → modules → core → shared`. Прикладные модули друг от
друга не зависят. Ядро не знает о прикладных модулях.

## Зависимости ядра от ядра

Разрешены только эти:

- `identity → throttle` — счёт неверных попыток входа;
- `throttle → jobs` — задание, которое удаляет отжившие счётчики;
- `identity → jobs` — задание, которое удаляет истёкшие коды и ожидающие входы;
- `membership → identity` — внешний ключ на аккаунт, аккаунты сидов;
- `membership → structure` — внешние ключи на узел и объект, вид узла, замок узла зоны;
- `authz → identity` — сессия запроса;
- `authz → membership` — активные привязки и назначения;
- `authz → structure` — предки узла и цепочка объекта;
- `membership → journal` — запись назначений и взятия зоны;
- `journal → structure` — внешние ключи на узел и объект, корень комплекса узла;
- `journal → authz` — пометка и действие чтения, область видимости;
- `journal → identity` — внешний ключ на аккаунт, имена авторов.

Новая зависимость ядра от ядра — вопрос владельцу проекта; после ответа она вносится в этот раздел.

Импорт только типов кольца не образует: `authz` берёт у `membership` одни типы, поэтому цепочка
`membership → journal → authz` не замыкается.
Модуль, от которого `journal` или `authz` зависят значениями, пишет в журнал через порт (`ports.md`, «Обратная зависимость»): так будет писать `identity`.

Глобальным модуль ядра делается, только когда он обязательный посредник, которым пользуется каждый модуль с данными дома:
`authz` и `journal`. Остальные модули импортируются явно.

## Публичный интерфейс

Всё, что модуль открывает другим, экспортируется из его `index.ts`: класс модуля, сервисы,
порты для других модулей, обработчики заданий, типы их входа и результата, таблица статусов ошибок. Остальное закрыто.
Другой модуль и `app/` импортируют только `index.ts`.

```ts
export { MembershipModule } from './membership.module.ts';
export { MembershipService } from './application/services/membership.service.ts';
export type { MembershipView } from './domain/entities/membership.entity.ts';
export { MEMBERSHIP_ERROR_STATUSES } from './presentation/membership.error-statuses.ts';
```

## Владение данными

- Модуль владеет своими таблицами. Его модели лежат в `prisma/schema/<модуль>.prisma`, и только его код к ним обращается.
- Чужие таблицы в запросах запрещены: другой модуль читает и меняет их только через интерфейс владельца.
- Исключение — справочные представления ядра (дерево, членство) для соединения в запросах.
  Каждое такое представление вносится в список `REFERENCE_VIEWS` теста владения.
  Представление разрешает только чтение: запись в чужую модель запрещена, что бы ни стояло в списке.
- Внешний ключ между модулями — только в сторону ядра: на аккаунт, узел, объект, членство, файл.
  Прикладные модули друг на друга не ссылаются: связь — id без внешнего ключа и интерфейс модуля.
- У каждого модуля своя схема PostgreSQL: `@@schema("<модуль>")` у каждой модели и enum. В `public` моделей нет.

## Как модули взаимодействуют

- **Синхронно** — вызов интерфейса в той же транзакции: `tx` передаётся первым параметром.
- **Отложенно** — задание, поставленное через `jobs` в той же транзакции. Последствия в другом прикладном модуле — всегда задание.
- Внутри транзакции нет сетевых вызовов, кроме базы.
- Обработчик задания идемпотентен: доставка — «не менее одного раза».

```ts
return this._transactions.run(async (tx) => {
    const ticket = await this._tickets.lockById(tx, ticketId);
    ticket.reopen(this._clock.now());
    await this._tickets.save(tx, ticket);
    await this._journal.record(tx, TICKET_REOPENED, {
        actor: actorOf(access),
        nodeId: ticket.view().ownerNodeId,
        details: { ticketId },
    });
    await this._jobs.enqueue(tx, TICKET_REOPENED_NOTICE, { ticketId });
});
```

## Обязательные посредники

- **Доступ** проверяет только `authz`. Область видимости приходит из него и стоит в сигнатуре каждого запроса к данным.
  Факты о ролях — привязки, назначения, «взял зону» — хранит и меняет только `membership`. Как этим пользоваться — `api.md`, «Доступ к данным дома».
  `AuthzModule` в `AppModule` стоит после `IdentityModule`: порядок модулей — порядок guard.
- **Внешние каналы** (SMS, push, почта) — только через `notify`.
- **Журнал действий** пишется только через `JournalService.record(tx, ДЕЙСТВИЕ, {…})` и только в транзакции своего изменения.
  Отказ записи откатывает изменение. Это не журнал событий `EventLogger` (`logging.md`): одно другого не заменяет.
    - Автора называет вызывающий: `actorOf(access)` или `SYSTEM_ACTOR` — сиды и скрипты. Последствие пишется с автором причины.
    - Повтор, который ничего не изменил, записи не даёт.
    - Тип действия объявляет модуль-владелец в `application/<модуль>.journal-actions.ts` значением `defineJournalAction`:
      имя `<модуль>.<что_случилось>`. Действие вносится в `src/app/journal-actions.ts`; действие не из списка не записывается.
    - В деталях — только id, целое до шести знаков, логическое и значение из списка, объявленного у действия.
      Имени, телефона и текста там нет: человек и объект называются полями `subjectAccountId` и `subjectUnitId`.
    - Читает журнал только модуль `journal`: своих лент действий модули не заводят.
- **Лимиты и неверные попытки** считает только `throttle`. Своих таблиц счётчиков модули не заводят.

## Лимиты и попытки

Счёт идёт по ключу: email, телефон, id объекта, адрес клиента. В таблицах `throttle` лежит отпечаток ключа, а не он сам.

- Правило объявляет модуль, которому оно нужно: числа лежат в его `domain/rules/`, само правило собирает
  `defineAttemptRule` или `defineRateLimit`. Имя правила попыток — `<модуль>.<что>`: `identity.admin_password`.
- **Частота** — `RateLimitService.spend(лимит, ключ)`: при превышении бросает 429 сам. Так считается и пауза
  перед повторным действием: всплеск 1 и время возврата, равное паузе.
- **Неверные попытки** — `AttemptLockService`, три шага:
    - `begin(правило, ключ)` до проверки: попытка засчитывается заранее, иначе параллельные запросы проверят больше, чем разрешено;
    - проверка выполняется всегда. Когда `attempt.isCounted` ложно, вход закрыт: сверка идёт с подставным значением,
      настоящий секрет не проверяется. Так ответ закрытого входа занимает столько же времени, сколько неверный;
    - при неудаче — `refusalOf(attempt)`: ошибка блокировки или `null`; при удаче — `clear(tx, правило, ключ)` в транзакции результата.
- Неизвестный ключ считается так же, как известный: по ответу нельзя понять, существует ли аккаунт.

```ts
const attempt = await this._attempts.begin(PASSWORD_ATTEMPTS, email);
const hash = attempt.isCounted ? storedHash : null;
const isVerified = await this._hasher.verify(password, hash ?? this._decoyHash);
if (hash === null || !isVerified) {
    throw (
        this._attempts.refusalOf(attempt) ??
        new IdentityError(
            'IDENTITY_CREDENTIALS_INVALID',
            'Email or password is incorrect',
        )
    );
}
await this._transactions.run(async (tx) => {
    await this._attempts.clear(tx, PASSWORD_ATTEMPTS, email);
    return this._sessions.start(tx, { accountId, application });
});
```

Как пометить эндпоинт лимитом по адресу — `api.md`.

## Взаимная зависимость и обработчики заданий

Если двум модулям ядра нужен друг друга, одно направление идёт через порт, а связь
стоит в `src/app/app-ports.module.ts`. Обработчик задания живёт в модуле, чья это работа,
и внесён в общий список `src/app/job-handlers.ts`. Подробности — `ports.md`.

## Проверяется автоматически

- oxlint:
    - из-за пределов модуля импортируются только `index.ts` модулей ядра, `shared/` и `generated/`;
    - прикладной модуль не импортирует другой прикладной, ядро не импортирует прикладные;
    - `app/` импортирует из модулей только `index.ts`;
    - циклы импортов.
- `test/unit/modules/table-ownership.spec.ts`: модель из `prisma/schema/<модуль>.prisma` вызывается
  и типизируется только в коде своего модуля; `shared/` не обращается ни к одной модели.
  Справочное представление другой модуль читает, запись в него тест ловит.
- `test/unit/schema/schema-conventions.spec.ts`: схема PostgreSQL модели и enum совпадает с именем файла схемы.
- `test/unit/jobs/job-handlers-registry.spec.ts`: каждый обработчик задания внесён в `src/app/job-handlers.ts`.
- `test/unit/journal/journal-actions-registry.spec.ts`: каждое действие из `*.journal-actions.ts` внесено в `src/app/journal-actions.ts`
  и названо по своему модулю; два действия с одним именем не дают приложению стартовать.
- `tsc`: детали записи журнала совпадают с объявлением действия.
- `test/e2e/journal/journal-records.e2e-spec.ts`: откат действия не оставляет записи; отказ записи не даёт действию состояться.
- `test/e2e/throttle/attempt-lock.e2e-spec.ts`: параллельные неверные попытки дают не больше проверок, чем разрешает правило;
  закрытый вход и неизвестный email отвечают так же, как неверный пароль.

Правила линта собирает `scripts/oxlint-config.ts`. `oxlint.json` руками не правится:
изменение вносится в скрипт, затем `npm run lint:config`. Расхождение ловит тест `test/unit/lint/`.

## Не проверяется

- Чужая таблица в сыром SQL или через связь в выборке.
- Внешний ключ между прикладными модулями.
- Сетевой вызов внутри транзакции; идемпотентность обработчика.
- Сравнение роли или узла в модуле в обход `authz`; внешний канал в обход `notify`.
- Запись в журнал действий вне транзакции изменения; `SYSTEM_ACTOR` там, где есть `access`; действие, для которого запись забыли.
  Эндпоинт без пометки доступа проверяется — см. `api.md`.
- Свой счётчик попыток или лимит в обход `throttle`; проверка секрета до `begin`; настоящий секрет, проверенный при закрытом входе.
- Зависимость между модулями ядра, о которой не спросили владельца проекта.
