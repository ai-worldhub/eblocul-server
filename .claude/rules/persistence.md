# Работа с базой

## Выборки

Какие поля читаются из базы, описывает константа в отдельном файле, а не объект в месте запроса.

- Файл: `infrastructure/<модель>.select.ts`. Константа: `<МОДЕЛЬ>_<НАЗНАЧЕНИЕ>_SELECT`.
- Тип проверяется по модели: `satisfies Prisma.<Модель>Select`. Опечатка в имени поля — ошибка компиляции.
- Тип результата выводится из выборки, а не пишется руками.
- В запросе стоит только константа: `findMany({ select: HOUSE_CARD_SELECT })`.

```ts
export const HOUSE_CARD_SELECT = {
    id: true,
    name: true,
    state: true,
    createdAt: true,
} satisfies Prisma.HouseSelect;

export type HouseCard = Prisma.HouseGetPayload<{
    select: typeof HOUSE_CARD_SELECT;
}>;
```

## Выборка и DTO совпадают

Если ответ повторяет выборку, в файле DTO стоит проверочная строка. Она сравнивает типы
в обе стороны и ломает компиляцию, когда они разошлись:

```ts
true satisfies [HouseCard] extends [House.Card]
    ? [House.Card] extends [HouseCard]
        ? true
        : false
    : false;
```

Если ответ отличается от выборки — вычисляемое значение, поле из связи, склейка — его
собирает маппер `presentation/mappers/<модель>.mapper.ts`. Функция возвращает объект-литерал:
только так `tsc` видит лишние и недостающие поля. Сервис маппер не вызывает.

```ts
export const toHouseResponse = (row: HouseCard): House.Response => ({
    id: row.id,
    title: row.name,
    isActive: row.state === 'active',
});
```

## Репозиторий

Нужен только вместе с entity — см. `layers.md`.

- Один репозиторий на entity, а не на таблицу. Связанные записи entity загружаются и сохраняются вместе с ней.
- Методы — загрузка entity (`findBy…`, `lockBy…`), `add(entity)`, `save(entity)` и удаление (`remove(entity)`, `removeBy…`). Запросов для экранов в нём нет.
- `add` отдельно от `save` нужен, когда вставка отличается от сохранения. Загрузка, которая создаёт запись, если её нет, называется `lockBy…OrAdd`.
- `addOrFind(entity)` — вставка сущности, id которой выбрал клиент: при повторе с тем же id она возвращает уже созданное.
  Совпадает ли повтор с первым вызовом, решает entity, а не репозиторий.
- `addOrFindActive(entity)` — вставка сущности, уникальной среди действующих: назначение, привязка. Её id выдаёт сервер;
  при повторе она возвращает действующую запись. Уникальность держит частичный уникальный индекс, написанный в SQL миграции:
  Prisma такой индекс не описывает, поэтому его имя записано строкой над моделью в файле схемы.
- Запись, уникальная по ключу, заменяется в одной транзакции: `removeBy…(ключ)`, затем `add(entity)`.
  Что два одновременных запроса не дойдут до вставки оба, держит правило выше по сценарию — пауза, замок, — и оно названо в описании PR.
- `holdBy…`, `holdActive` — загрузка записи, которую транзакция только держит (`FOR SHARE`). `lockBy…` — для записи, которую транзакция меняет.
- Принимает и возвращает только entity. Типы Prisma наружу не выходят.
- Абстрактный класс в `ports/<предмет>.repository.ts`, реализация в `infrastructure/prisma/`, связь в `<модуль>.module.ts` — см. `ports.md`.
- Строка базы и состояние entity сверены такой же проверочной строкой.

### Хранилище без entity

Entity не заводится, когда вся операция — один атомарный оператор базы и между чтением и записью
в памяти ничего не решается: счётчик, взятие жетона.

- Порт — в `ports/<предмет>.repository.ts`, метод назван по действию: `RateBucketRepository.takeToken`.
- Метод принимает значения и правило из `domain/` и возвращает исход операции. Что делать с исходом, решает `domain/` или сервис.
- В таком порту только эти операции. Запросов для экранов и загрузки строк в нём нет.
- Как только появляется решение между чтением и записью — это entity и обычный репозиторий.

## Чтение сырым SQL

Сырой SQL нужен, когда чтение не выразить выборкой одним запросом: обход дерева, объединение разнородных строк,
запрос, план которого проверяет тест.

- Порт — `ports/<что>-queries.port.ts`, абстрактный класс `…Queries`. Реализация — `infrastructure/prisma/<что>-queries.ts`.
  Сервис зависит от порта: `application/` сырой SQL не пишет.
- Текст запроса — отдельная экспортируемая функция, которая возвращает `Prisma.sql`. По ней тест получает план.
- Параметры подставляет только `Prisma.sql`. Склейки строк нет.
- Таблицы и типы названы со схемой. Значение enum приводится к тексту в самом запросе: `kind::text`.
- Тип строки объявлен рядом с запросом, имена полей — как колонки в запросе. В нём только колонки, которые читает маппинг:
  служебные — для сортировки или выравнивания ветвей объединения — в тип не входят.
- Наружу порт отдаёт типы из `domain/`, а не строку.
- Сверить тип строки с запросом компилятор не может. Поля, которые порт отдаёт наружу, держит e2e-тест сценария: он сравнивает результат целиком.

## Транзакции

Транзакцию открывает только `Transactions.run` из `shared/db`: там в одном месте заданы время ожидания
соединения и предел длительности. Напрямую `$transaction` не вызывается.
Транзакция передаётся явно, первым параметром `tx` типа `Tx` из `shared/db/tx.ts`, в каждый вызов, который должен в неё попасть.

```ts
return this._transactions.run(async (tx) => {
    const code = await this._codes.lockById(tx, codeId);
    code.use(this._clock.now());
    await this._codes.save(tx, code);
    return code.view();
});
```

- Внешние вызовы — SMS, push, хранилище — внутри транзакции не делаются.
- Правило «проверил — защитил»: запись, по которой принято решение, блокируется в той же транзакции.
- Замок по умолчанию — `FOR UPDATE`. Если на запись ссылаются внешние ключи, а транзакция её не удаляет и ключ не меняет,
  берётся `FOR NO KEY UPDATE`: `FOR UPDATE` ждёт проверок внешних ключей из других транзакций,
  и два параллельных создания дочерних строк дают взаимную блокировку.
- Запись, по которой принято решение и которую транзакция не меняет, держится `FOR SHARE`:
  он останавливает её изменение и не выстраивает читателей в очередь. Так держится основание доступа в транзакции изменения.
- Запись, которую транзакция изменит, сразу берётся замком для изменения. Взять `FOR SHARE` и потом менять нельзя:
  две такие транзакции ждут друг друга, пока база не оборвёт одну.
- Строку, от состояния которой зависят разные операции, все они берут одним и тем же замком:
  «взять зону», назначение администратора зоны и прекращение его роли берут узел зоны `FOR NO KEY UPDATE`.
  Операция, которая сначала берёт свою запись, а потом общую строку, называет этот порядок в описании PR.
- Условие «такой записи нет» замком строки не защитить. Оно перечитывается в транзакции, и последствие гонки называется в описании PR.
- Библиотек, которые подставляют транзакцию незаметно, нет.
- Транзакция живёт не дольше пяти секунд. Работа, которой нужно больше, делится на шаги или уходит в задание.

## Часовой пояс сессии

Клиент Prisma отправляет даты текстом в UTC без смещения и читает `timestamptz`, отбрасывая смещение.
Поэтому время верно только в сессии с поясом UTC: в другом поясе оно сохраняется со сдвигом,
а в ночь перевода часов два разных момента сохраняются одним.

- Сессия базы всегда в UTC, каким бы ни был пояс сервера PostgreSQL.
- Пояс закрепляет `DbService`: дописывает `-c timezone=UTC` последним в параметр `options` адреса базы.
  Свои `options` в `DATABASE_URL` сохраняются. При старте `DbService` читает `TimeZone` и не запускается, если он не `UTC`.
- `prisma.config.ts` дописывает тот же параметр для сессий `prisma migrate`. Строки там повторены, а не импортированы:
  в образ попадает `prisma.config.ts`, но не `src/`. Меняется одно место — меняется и второе.
- К базе подключается только `DbService`. Другой клиент Prisma или пул соединений в `src/` не создаётся.
- `SET TIME ZONE` в запросах и миграциях не пишется.
- В сыром SQL нет выражений, результат которых зависит от пояса сессии: приведения `timestamptz` к `timestamp` или `date`,
  `date_trunc` без пояса, литерала времени без смещения. Пояс комплекса передаётся в выражение явно: `AT TIME ZONE`.

## Проверяется автоматически

- `tsc`: поля выборки существуют в модели; код не читает поле вне выборки; выборка
  совпадает с DTO и строка базы с entity — там, где стоит проверочная строка; маппер не теряет и не добавляет поля.
- oxlint: `$transaction` вне `src/shared/db/` запрещён.
- `test/e2e/db/transactions.e2e-spec.ts`: успешная работа сохраняется и возвращает результат; исключение откатывает всё и проходит наружу.
- Запуск приложения: `DbService` отказывается работать, если пояс сессии не `UTC`.
- `test/e2e/db/session-time-zone.e2e-spec.ts`: при поясе базы `Europe/Chisinau` сессии приложения и миграций остаются в UTC;
  типизированная запись и сырое чтение сходятся, и наоборот; `options` из адреса сохраняются; сессия не в UTC отклоняется.
- `test/unit/db/utc-session.spec.ts`: параметр дописывается последним, остальной адрес не меняется.

## Не проверяется

- Объект `select` прямо в запросе вместо константы.
- Что у выборки, уходящей в ответ, есть проверочная строка или маппер.
- Что тип строки сырого запроса совпадает с его колонками; что выбран нужный вид замка.
- Секретные поля в выборке для ответа.
- Внешний вызов внутри транзакции; решение по незаблокированной записи.
- Второй клиент Prisma или пул в `src/`; `SET TIME ZONE` и выражения, зависящие от пояса сессии, в сыром SQL и миграциях.
- Что строки закрепления пояса в `prisma.config.ts` и `src/shared/db/utc-session.ts` совпадают.
