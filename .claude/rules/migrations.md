# Миграции и схема

## Как меняется схема

- Только миграциями: `npm run prisma:migrate -- --name <имя>`. Схема и папка миграции коммитятся вместе.
- `prisma db push` — только на своей локальной базе, чтобы что-то попробовать.
- Имя миграции — по смыслу изменения, на английском, snake_case, с глаголом: `add_house_state`, `drop_user_legacy_name`.
- Слитая миграция не редактируется, не переименовывается и не удаляется. Исправление — новой миграцией. Обратных миграций нет.

## Есть ли уже пользователи

Разделы «Совместимость с предыдущей версией» и «Блокировки и данные» действуют только
когда у продукта есть пользователи: развёрнуто окружение с настоящими данными, которое
нельзя остановить или пересоздать. Пока пользователей нет, несовместимое изменение
делается одной миграцией в одном выпуске.

Перед несовместимым изменением схемы — удалить, переименовать, сменить тип, сделать
обязательным — Claude спрашивает, есть ли уже пользователи. Ответ не предполагается
и не переносится из прошлых задач: стадия проекта меняется.

Остальные разделы действуют всегда.

## Совместимость с предыдущей версией

Миграция выполняется до запуска новой версии, пока работает старая. Откат возвращает
прошлый образ, но не схему. Поэтому каждая миграция совместима с предыдущей версией приложения.

| Изменение                           | Выпуски                                                                |
| ----------------------------------- | ---------------------------------------------------------------------- |
| Новая таблица, необязательное поле  | один                                                                   |
| Удалить поле или таблицу            | два: код перестаёт читать и писать; следующий выпуск удаляет           |
| Переименовать поле или таблицу      | три: добавить новое; перевести код; удалить старое                     |
| Сделать поле обязательным           | два: заполнить и всегда писать; следующий выпуск ставит `NOT NULL`     |
| Новое значение enum или вид задания | два: сначала код умеет его читать; записывать начинают на выпуск позже |

## Блокировки и данные

- Миграция короткая и не держит долгих блокировок.
- Индекс на существующей таблице — `CREATE INDEX CONCURRENTLY`, отдельной миграцией.
- Перенос данных — фоновое задание, а не миграция.

## Транзакция

Prisma не оборачивает миграцию в транзакцию: миграция, упавшая на середине, оставляет
в базе всё, что успела сделать.

- Миграция из нескольких шагов, которые имеют смысл только вместе, сама пишет `BEGIN;` и `COMMIT;`.
- `CREATE INDEX CONCURRENTLY` в транзакции не работает — ему нужна отдельная миграция без неё.

## Схема

Как писать модели, типы, связи и индексы — `schema.md`.

## Проверяется автоматически

- CI: схема совпадает с миграциями (`prisma migrate diff --exit-code`).
- e2e применяет все миграции к чистой базе.

## Не проверяется

- Что перед несовместимым изменением был задан вопрос о пользователях.
- Совместимость с предыдущей версией приложения; число выпусков для несовместимого изменения.
- Что слитую миграцию не изменили; имена миграций.
- Транзакция у многошаговой миграции; длительность блокировок.
